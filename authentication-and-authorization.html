    8. Authentication and Authorization

    Two distinct questions arise for each request:

    • Who is the user? This is authentication: the user has identified themselves with a username and password, and every subsequent request must prove that it comes from them;
    • Do they have permission to access this page? This is authorization: in the case study, only a user with the role ADMIN manages doctors and clients.

    Since the server is stateless (see the chapter on scopes), proof of identity must be included with every request. A token named JWT (*JSON Web Token*) is used: After login, the server generates a token containing the user’s identity and signs it with a secret key. The token is stored in a cookie; the browser sends it back with every request; the server verifies the signature. The user can read their token but cannot modify it: any modification invalidates the signature. This is the same principle as the [Flask] session (Example 20), but with a standardized format (RFC 7519) that is understood by all programming languages, and an expiration date embedded in the token.

    [Flask] does not have a built-in security mechanism, unlike [Spring] ([Spring Security]) or [ASP.NET Core]. Extensions exist ([Flask-Login], [Flask-JWT-Extended]...), but the mechanism is simple enough to be written by hand using the tools from the previous chapters, which has the advantage of making it transparent:

    • authentication is handled by a function [before_request] (previous chapter), which retrieves the token from the cookie, verifies it, and stores the authenticated user in [g], the request object;
    • authorization is handled by decorators applied to the actions ([@connexion_requise], [@role_requis("ADMIN")]), built like the [@avec_langue] decorator in Example 12.

    Two libraries are used, installed by the [requirements.txt] file from the examples: [PyJWT], which generates and verifies tokens, and [bcrypt], which hashes passwords.

from dataclasses import dataclass

import bcrypt


@dataclass(frozen=True)
class Utilisateur:
    login: str
    nom: str
    role: str
    hachage_mot_de_passe: bytes


# password hashing: bcrypt, with a cost of 10 (2^10 rounds);
# gensalt generates a random “salt,” which is stored within the hash itself
def hacher(mot_de_passe: str) -> bytes:
    return bcrypt.hashpw(mot_de_passe.encode(), bcrypt.gensalt(rounds=10))


class UtilisateursService:

    def __init__(self):
         # We do not store JAMAIS a password, only its hash
        self._utilisateurs = {u.login: u for u in (
            Utilisateur("marie", "Marie Pélissier", "USER", hacher("marie")),
            Utilisateur("admin", "Administrateur", "ADMIN", hacher("admin")),
        )}

    def chercher(self, login: str) -> Utilisateur | None:
        return self._utilisateurs.get(login)
    • Lines 9–13: a user: their login, name, role, and password hash. A server never stores a password, even in encrypted form: if the database were stolen, the passwords would be too (and many people use the same password everywhere). It stores the result of a hash function, a one-way function: you can calculate the hash of a password, but you cannot recover a password from its hash. To verify an entered password, you calculate its hash and compare it to the one on file;
    • lines 18–19: hashing using the [bcrypt] algorithm, designed for passwords. It has two distinctive features. It is intentionally slow, with an adjustable slowness (the parameter [rounds], or cost: 2^10 computation cycles): a few tens of milliseconds, imperceptible to a user, but which makes it very costly for a hacker to try billions of passwords. It uses a salt: [gensalt] randomly generates a salt, mixes it with the password before hashing, and stores it within the hash itself; thus, two users with the same password will have different hashes. [bcrypt] operates on bytes: [encode()] converts the string into bytes ([UTF-8]). It considers only the first 72 bytes of a password, and version 5 of the library rejects longer passwords (the case study takes this into account);
    • Lines 26–28: two test users, stored in memory, organized in a dictionary built during processing ([{clé: valeur for ...}]). Example 28 and the case study will store them in a database.

    # auth/service.py: password verification and tokens JWT
from datetime import datetime, timedelta, timezone

import bcrypt
import jwt
from flask import current_app

from auth.utilisateurs import Utilisateur, UtilisateursService

# the name of the cookie that carries the token
COOKIE = "jeton"


class AuthService:

    def __init__(self, utilisateurs: UtilisateursService, secret: str, duree_minutes: int):
        self._utilisateurs = utilisateurs
        self._secret = secret
        self.duree = timedelta(minutes=duree_minutes)

     # the user, or None if the login is unknown or the password is incorrect.
     # checkpw hashes the entered password with the stored hash salt,
     # then compares the two results
    def valider(self, login: str | None, mot_de_passe: str | None) -> Utilisateur | None:
        if not login or mot_de_passe is None:
            return None
        utilisateur = self._utilisateurs.chercher(login)
        if utilisateur is None or not bcrypt.checkpw(mot_de_passe.encode(),
                                                     utilisateur.hachage_mot_de_passe):
            return None
        return utilisateur

     # the user’s token (JWT), signed with the secret key (HMAC-SHA256)
    def creer_jeton(self, utilisateur: Utilisateur) -> str:
        maintenant = datetime.now(timezone.utc)
         # the token’s content: the “claims” (statements about the user)
        claims = {
            "sub": utilisateur.login,
            "nom": utilisateur.nom,
            "role": utilisateur.role,
            "iat": maintenant,
            "exp": maintenant + self.duree,
        }
        return jwt.encode(claims, self._secret, algorithm="HS256")

     # the claims of a token whose signature and expiration date are
     # valid; None otherwise (token is forged, expired, or unreadable)
    def verifier(self, jeton: str) -> dict | None:
        try:
            return jwt.decode(jeton, self._secret, algorithms=["HS256"])
        except jwt.InvalidTokenError:
            return None


def auth_service() -> AuthService:
    return current_app.extensions["auth"]
    • Lines 24–31: Verification of a username and password. [bcrypt.checkpw] hashes the entered password using the stored hash salt and compares the two hashes. An unknown username and an incorrect password yield the same result, [None];
    • lines 34–44: generating the token. Its content is a dictionary of claims about the user. Some have standardized names: [sub] (*subject*), the user’s identifier; [iat] (*issued at*), the creation date; [exp] (*expiration*), the expiration date. The others are arbitrary: in this case, the name and role. [jwt.encode] generates the token and signs it using the algorithm [HS256] (HMAC-SHA256, a signature using a shared secret key). Dates must be time-zone-aware dates: [datetime.now(timezone.utc)];
    • Lines 48–30: Token verification. [jwt.decode] verifies the signature and expiration date, then returns the assertions. Any anomaly (forged, expired, or malformed token) raises an exception from the [InvalidTokenError] family. The [algorithms] parameter specifies the accepted algorithms: without it, an attacker could create a token that declares a different algorithm (or even none at all, [none]).

    # auth/securite.py: the user for each request, and protection of actions
from functools import wraps

from flask import g, redirect, request, url_for

from auth.service import COOKIE, auth_service


def enregistrer(app):

     # before each action: the cookie token -> g.utilisateur (its claims), or None
    @app.before_request
    def lire_jeton():
        jeton = request.cookies.get(COOKIE)
        g.utilisateur = auth_service().verifier(jeton) if jeton else None


# a decorator: the action is executed only for an authenticated user;
# otherwise, redirect to the login page
def connexion_requise(action):
    @wraps(action)
    def action_protegee(*args, **kwargs):
        if g.utilisateur is None:
            reponse = redirect(url_for("auth.formulaire"))
             # a cookie is present but invalid (expired or forged token): it is deleted
            if COOKIE in request.cookies:
                reponse.delete_cookie(COOKIE)
            return reponse
        return action(*args, **kwargs)

    return action_protegee
    • lines 13–15: Before each action, the cookie token is verified; [g.utilisateur] contains the claims of a valid token, or [None]. This function does not reject anything: it establishes who the user is. This is authentication;
    • lines 20–31: the decorator that requires an authenticated user. For an anonymous visitor, it does not return the action but instead redirects to the login page. If the browser sent a cookie, it means the token is invalid (expired or forged): we take this opportunity to delete it ([delete_cookie] sends an empty cookie that has already expired).

from flask import Blueprint, redirect, render_template, request, url_for

from auth.service import COOKIE, auth_service

auth = Blueprint("auth", __name__)


@auth.get("/")
def accueil():
    return redirect(url_for("profil.afficher"))


@auth.get("/login")
def formulaire():
    return render_template("auth/login.html")


@auth.post("/login")
def connexion():
    login = request.form.get("login")
    utilisateur = auth_service().valider(login, request.form.get("motDePasse"))
    if utilisateur is None:
         # A deliberately vague message: it doesn’t specify whether it’s the username or the password
        return render_template("auth/login.html", login=login,
                               erreur="Login ou mot de passe incorrect.")
    reponse = redirect(url_for("profil.afficher"))
     # the token, stored in a cookie: the page’s JavaScript cannot read it
     # (httponly); it is not included in requests like POST coming from other sites
     # (samesite); it disappears when the token expires (max_age)
    reponse.set_cookie(COOKIE, auth_service().creer_jeton(utilisateur), httponly=True,
                       samesite="Lax", max_age=auth_service().duree)
    return reponse


# Logout: POST only (a simple link placed on another site
# log the user out without their knowledge); the cookie is deleted
@auth.post("/logout")
def deconnexion():
    reponse = redirect(url_for("auth.formulaire"))
    reponse.delete_cookie(COOKIE)
    return reponse
    • lines 20–26: the login. If the login fails, the form is redisplayed with the entered username and a deliberately vague message: saying “unknown username” would reveal to a hacker which usernames exist;
    • lines 27–32: if successful, the token is stored in a cookie, with a redirect to the protected page (schema PRG). The cookie is [httponly]: the page’s [JavaScript] cannot read it, which protects the token against script injection (XSS); it is [samesite="Lax"]: the browser does not send it with a POST request originating from another site, which protects the application against CSRF attacks (example 18); its lifetime ([max_age], which accepts a [timedelta]) is that of the token. In production, for HTTPS, we would add [secure=True]: the cookie would never be sent over an unencrypted connection;
    • lines 38–41: Logging out deletes the cookie. This is a POST action: a simple link to [/logout], placed on another site or within an image, cannot log the user out without their knowledge. Note a limitation of tokens: the token itself remains valid until it expires. Someone who has made a copy of it could still use it. That is why their lifetime is limited.

    8.3. Example 27: CAPTCHA and Attempt Limits

    A login form is a target: a program can try thousands of passwords per minute (brute-force attack). Two protections complement each other:

    • a CAPTCHA (*Completely Automated Public Turing test to tell Computers and Humans Apart*): an image containing a distorted code that is easy for a human to read but difficult for a program;
    • an attempt limit: after three failed attempts, the client’s address IP is blocked for one minute.

    Example 27 is based on Example 25 (without the administration page) and adds these two security measures.

                f'viewBox="0 0 {LARGEUR} {HAUTEUR}">',
                 '<rect width="100%" height="100%" fill="#f5f7fa"/>']

     # The characters: each enlarged, tilted, and offset, and each dot
     # slightly shifted at random
    pas = (LARGEUR - 20) / len(texte)
    for i, caractere in enumerate(texte):
        echelle = hasard(4.6, 5.6)  # one grid unit in pixels
        angle = hasard(-0.35, 0.35)  # rotation, in radians (approximately ±20°)
        cx = 10 + pas * (i + 0.5) + hasard(-3, 3)  # center of the character
        cy = HAUTEUR / 2 + hasard(-4, 4)
        d = []
        for trait in POLICE[caractere]:
            for k in range(0, len(trait), 2):
                 # grid point, centered at (2, 3), distorted, rotated, positioned
                x = (trait[k] - 2 + hasard(-0.2, 0.2)) * echelle
                y = (trait[k + 1] - 3 + hasard(-0.2, 0.2)) * echelle
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
        morceaux.append(f'<path d="{" ".join(d)}" fill="none" stroke="{couleur()}" '
                        f'stroke-width="{hasard(2.2, 3):.1f}" stroke-linecap="round" '
                        f'stroke-linejoin="round"/>')

     # 3 scrambling lines: curves that cross the image
    for _ in range(3):
        morceaux.append(
            f'<path d="M{hasard(0, 20):.1f} {hasard(5, 45):.1f} '
            f'C{hasard(30, 60):.1f} {hasard(0, 50):.1f} {hasard(90, 120):.1f} {hasard(0, 50):.1f} '
            f'{hasard(130, 150):.1f} {hasard(5, 45):.1f}" fill="none" stroke="{couleur()}" '
            f'stroke-width="1.3"/>')

import secrets
from dataclasses import dataclass
from datetime import datetime, timedelta
from threading import Lock

from flask import current_app

from auth import dessin_captcha

DUREE_VIE = timedelta(minutes=10)


# a CAPTCHA: its ID and its image (SVG)
@dataclass(frozen=True)
class Captcha:
    id: str
    svg: str


class CaptchaService:

    def __init__(self):
         # ID -> (expected response, expiration date)
        self._en_attente: dict[str, tuple[str, datetime]] = {}
        self._verrou = Lock()

    def generer(self) -> Captcha:
        texte = dessin_captcha.texte_aleatoire(5)
        id = secrets.token_urlsafe(16)  # a random identifier, impossible to guess
        with self._verrou:
            self._en_attente[id] = (texte, datetime.now() + DUREE_VIE)
        return Captcha(id, dessin_captcha.svg(texte))

     # The CAPTCHA is CONSOMMÉ in all cases: an image is used only once
    def verifier(self, id: str | None, saisie: str | None) -> bool:
        with self._verrou:
            attendu = self._en_attente.pop(id, None) if id else None
        if attendu is None or saisie is None:
            return False
        texte, expire = attendu
        return expire > datetime.now() and texte.lower() == saisie.strip().lower()


def captcha_service() -> CaptchaService:
    return current_app.extensions["captchas"]

    • lines 36–42: verification. [pop] removes the entry from the dictionary and returns it: the CAPTCHA is consumed in all cases, whether successful or not. Without this, a program could try every possible answer on the same image. The comparison ignores case and spaces around the input.

    This service keeps data in memory on the server: this is a departure from the stateless server principle (see the chapter on scopes), which is acceptable for short-lived data.     # auth/limiteur.py: counts the number of failed login attempts for each address IP
import math
from datetime import datetime, timedelta
from threading import Lock

from flask import current_app

MAX_ECHECS = 3
DUREE_BLOCAGE = timedelta(minutes=1)


class Compteur:
    def __init__(self):
        self.echecs = 0
        self.bloque_jusqua = datetime.min


class LimiteurService:

    def __init__(self):
        self._compteurs: dict[str, Compteur] = {}
         # multiple simultaneous requests, only one access at a time
        self._verrou = Lock()

     # number of seconds remaining until lockout (0: not locked out)
    def secondes_blocage(self, ip: str) -> int:
        with self._verrou:
            compteur = self._compteurs.get(ip)
            if compteur is None:
                return 0
            reste = (compteur.bloque_jusqua - datetime.now()).total_seconds()
            return max(0, math.ceil(reste))

    def echec(self, ip: str):
        with self._verrou:
            compteur = self._compteurs.setdefault(ip, Compteur())
            compteur.echecs += 1
            if compteur.echecs >= MAX_ECHECS:
                compteur.bloque_jusqua = datetime.now() + DUREE_BLOCAGE
                compteur.echecs = 0  # After the lockout, the count resets to zero

    def reussite(self, ip: str):
        with self._verrou:
            self._compteurs.pop(ip, None)


def limiteur_service() -> LimiteurService:
    return current_app.extensions["limiteur"]
    • lines 12–15: for each address IP, a number of failed attempts and an end-of-block date ([datetime.min], the earliest possible date, means “not blocked”);
    • lines 26–32: the number of seconds remaining in the lock, rounded up to the nearest whole number ([math.ceil]);

    • lines 42–44: A successful connection clears the counter.
