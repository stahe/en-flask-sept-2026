    4. The view and its model

    Until now, actions generated their own responses: text, JSON, and a few HTML tags written in a string. In a MVC application, this is the role of a view: a file that describes the page HTML, with placeholders for the data passed to it by the action—the view model.

    [Flask] comes with a view engine, [Jinja2], written by the same team (the *Pallets* project). Other engines can be used ([Mako], [Chameleon]...), but [Jinja2] is by far the most widely used in [Python]: it is found in [Django] (as an option), in [Ansible], in static site generators... This is the one used in this course.

    A [Jinja2] view (the documentation refers to it as a *template*, a page template) is a text file—in this case, HTML—in which three types of tags are interpreted on the server:

    • [{{ expression }}]: the value of an expression, inserted into the page;
    • [{% instruction %}]: an instruction: condition ([if]), loop ([for]), template inheritance ([extends], [block]), inclusion ([include]), macro...;
    • [{# comment #}]: a comment that does not appear on the generated page.

    Everything else is copied as-is. The syntax of the expressions is similar to that of [Python]. This differs from [Thymeleaf], the view engine for course [Spring MVC], whose views are valid HTML files enriched with [th:] attributes; Instead, it brings [Jinja2] closer to [Razor] ([ASP.NET Core MVC]), which mixes HTML and code. By default, [Flask] searches for views in the application’s [templates] folder.

from datetime import datetime

from flask import Blueprint, render_template

from models.page import PageModel

views = Blueprint("views", __name__)


# render_template: the Jinja2 engine builds the page from the view
# templates/views/index.html and from the variables passed as keyword parameters
# (here a single one, [model]); the produced page is the response of the action
@views.get("/")
def index():
    model = PageModel(
        "My first view",
        "This page was built by Jinja2, on the server.",
        datetime.now().strftime("%H:%M:%S"))
    return render_template("views/index.html", model=model)


# the same view with another model; or another view, with the 404 code
@views.get("/hello/<name>")
def hello(name):
    if name == "unknown":
        # a tuple (page, code): the page, sent with the 404 code
        return render_template("views/unknown.html", name=name), 404
    model = PageModel(
        f"Hello {name}",
        "This time, the title of the page comes from the URL.",
        datetime.now().strftime("%H:%M:%S"))
    return render_template("views/index.html", model=model)
    • line 4: imports the function [render_template];
    • lines 16–19: the action builds the view model. [datetime.now().strftime("%H:%M:%S")]: the current time, formatted (see Example 12);
    • line 20: [render_template] instructs [Jinja2] to generate the page: the first parameter is the view path, relative to the [templates] folder; the named parameters that follow are the view’s variables; in this case, there is only one: [model]. [render_template] returns the text of the generated page, which becomes the action’s response (of type [text/html]);
    • line 28: another view, with a different variable ([name]). The tuple [(page, 404)] sends the page with a 404 status code (see Example 03): a custom error page;
    • Lines 29–33: the same view as the action [index], with a different template. This is the benefit of separating actions from views: a single view can be used by multiple actions.

    # app.py: the application of example 14
from flask import Flask

from controllers.basics import basics


def create_app():
    app = Flask(__name__)
    # the {% ... %} tags leave no blank lines in the produced page:
    # trim_blocks removes the line break that follows a tag, lstrip_blocks the
    # spaces that precede it on its line
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    app.register_blueprint(basics)
    return app


if __name__ == "__main__":
    create_app().run(port=5000, debug=True)
    • Lines 12–13: [app.jinja_env] is the application’s [Jinja2] environment—the object that loads and executes the views. By default, a [{% %}] tag standing alone on its line leaves the spaces preceding it and the line break following it in the generated page: a loop would produce numerous empty lines. [trim_blocks] removes the line break following a tag, while [lstrip_blocks] removes the spaces preceding it. These two settings do not affect the page’s display (the browser ignores these whitespace characters), but they make the generated HTML more readable. All of the following examples enable them.

    <!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>{{ model.title }}</title>
</head>
<body>
  {# {% set %}: a variable of the view; the filters (|) transform a value #}
  {% set total = model.products | sum(attribute="price") %}
  {% set count = model.products | length %}
  <h1>{{ model.title }}</h1>
  {# 1. display a value of the model; None is displayed... "None": the filter
        default(text, true) replaces an empty or None value. This Jinja2
        comment does not appear in the produced page #}
  <p>1. Name: {{ model.name }} - nickname: [{{ model.nickname }}] [{{ model.nickname | default("", true) }}]</p>
  {# 2. {{ }} escapes HTML; the safe filter inserts it as is #}
  <p>2a. {{ model.html }}</p>
  <p>2b. {{ model.html | safe }}</p>
  {# 3. a condition #}
  {% if model.logged_in %}
  <p>3. You are logged in.</p>
  {% else %}
  <p>3. You are not logged in.</p>
  {% endif %}
  {# 4. a loop: [loop] describes the state of the loop #}
  <p>4. Our products:</p>
  <ul>
    {% for product in model.products %}
    <li>no. {{ loop.index0 }}: {{ product.name }}, {{ product.price }} {{ model.currency }}
      {{ "(in stock)" if product.in_stock else "(sold out)" }}
      {% if loop.first %}- the first one{% endif %}
      {% if loop.last %}- the last one, seen by {{ model.name }}{% endif %}
    </li>
    {% endfor %}
  </ul>
  {# 5. the empty list: the else block of a for loop #}
  <p>5. Your cart:
    {% for p in model.cart %}<span>{{ p.name }}</span>{% else %}it is empty.{% endfor %}
  </p>
  {# 6. computed expressions, the set variables, and the format filter #}
  <p>6. {{ count }} products, for a total of {{ total }} {{ model.currency }};
    average price: {{ "%.2f" | format(total / count) }} {{ model.currency }}</p>
  {# 7. an object inside an object, and a Python method (upper) #}
  <p>7. Address: {{ model.address.street }}, {{ model.address.city.upper() }}</p>
  <p>8. An email address: contact@example.com</p>
</body>
</html>
    • Lines 9–10: [{% set %}] creates a view variable. Filters transform a value: [value | filter] or [value | filter(parameters)]. The filter [sum(attribute="price")] sums the [price] attributes of the elements in a list; the filter [length] returns the length of a list. [Jinja2] provides about fifty filters: [upper], [lower], [title], [trim], [join], [sort], [round], [default], [replace], [truncate]... ;
    • line 15: the value [None] is displayed... [None]. The filter [default(value, true)] replaces an “empty” value ([None], empty string, zero) with the specified value; without the second parameter [true], it would only replace an undefined variable;
    • lines 17–18: [{{ }}] escapes HTML (2a); the filter [safe], on the other hand, declares that the value is safe HTML, to be inserted as-is (2b). [safe] is reserved for HTML generated by the application itself, never for user input;
    • lines 20–24: a condition: [{% if %}], [{% elif %}], [{% else %}], [{% endif %}]. Unlike [Python], whose blocks are delimited by indentation, [Jinja2] closes each block with a [end...] tag;
    • lines 28–34: a loop [{% for %}] ... [{% endfor %}]. Within the loop, the special variable [loop] describes the loop’s state: [loop.index] (the iteration number, starting at 1), [loop.index0] (starting at 0), [loop.first], [loop.last] (true on the first and last iterations), [loop.length] (the number of elements). Variables outside the loop ([model.name]) remain accessible;
    • line 30: the conditional expression for [Python], [a if condition else b], is also that of [Jinja2];
    • Line 38: A [for] loop can contain a [{% else %}] block, which is executed if the list is empty. This is simpler than a [if] that would check the length of the list;
    • Lines 41–42: calculated expressions ([total / count]). The filter [format] applies a format similar to the [%] operator from [Python]: ["%.2f"] displays a number with two decimal places. In Example 16, we’ll see a much better way to format numbers and amounts;
    • line 44: dot notation traverses objects ([model.address.city]) and allows you to call their methods: [upper()] is a method of the strings [Python];
    • line 45: an email address, written as-is. The character [@], which has a specific meaning in other view engines ([Razor]), has no such meaning in [Jinja2]: only the tags [{{ }}], [{% %}], and [{# #}] are interpreted.

    # app.py: the application of example 15
from datetime import date
from pathlib import Path

from flask import Blueprint, Flask, request

from controllers.pages import pages

# Bootstrap, shared by the examples: the examples/common/bootstrap folder,
# designated from the location of THIS file (and not from the current folder)
BOOTSTRAP = Path(__file__).resolve().parent.parent / "common" / "bootstrap"


def create_app():
    app = Flask(__name__)
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # a blueprint without routes, which only serves static files: the
    # BOOTSTRAP folder, under the /bootstrap/... URL
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(pages)

    # a "context processor": executed before building EACH view,
    # it adds its variables to the model of all the views
    @app.context_processor
    def common_model():
        return {"path": request.path, "year": date.today().year}

    return app

from flask_wtf import FlaskForm
from wtforms import EmailField, IntegerField, PasswordField, StringField
from wtforms.validators import DataRequired, Email, EqualTo, InputRequired, Length, NumberRange


# a FILTER: it transforms the received value BEFORE the validation;
# here, the spaces that surround the input are removed
def clean(value):
    return value.strip() if isinstance(value, str) else value


class RegistrationForm(FlaskForm):

    # the language of the messages that WTForms writes itself (impossible conversion,
    # for example: "abc" in an integer field)
    class Meta:
        locales = ["en"]

    # each field: a label, filters, and a list of validators, each one
    # with its error message. DataRequired rejects an empty input (or one made
    # of spaces); it also produces the HTML5 [required] attribute
    name = StringField("Name", filters=[clean], validators=[
        DataRequired("The name is required."),
        Length(max=20, message="The name must not exceed 20 characters.")])

    # EmailField: an <input type="email"> field
    email = EmailField("Email address", filters=[clean], validators=[
        DataRequired("The email address is required."),
        Email("Invalid email address.")])

    # everything that comes from a form is a string: IntegerField converts it
    # ("42" -> 42); InputRequired: the input must not be empty
    age = IntegerField("Age", validators=[
        InputRequired("The age is required."),
        NumberRange(min=18, max=120, message="The age must be between 18 and 120 years.")])

    password = PasswordField("Password", validators=[
        DataRequired("The password is required."),
        Length(min=6, message="The password must have at least 6 characters.")])

    # a rule about TWO fields: EqualTo compares this field with another one
    confirmation = PasswordField("Confirmation", validators=[

    4.8. Example 20: The Post/Redirect/Get Pattern

    When a POST action responds with a page, that page is the result of a POST. If the user reloads the page (presses [F5]), the browser sends the POST request, after displaying a warning that few people read: the command is sent twice, and the message is posted twice. The Post/Redirect/Get pattern (PRG) avoids this problem: a successful POST action does not return a page; it responds with a redirect (example 04) to a page GET, which the browser requests immediately. Reloading this page simply re-executes the GET action.

    There is still one problem: the page GET wants to display a message (“the task has been added”), but it is the action POST that knows this message, and it cannot pass a variable to a request that has not yet occurred. The solution: a flash message, posted by the POST action, retained until the next request, displayed, and then discarded.

from dataclasses import dataclass, replace
from threading import Lock

from flask import current_app


# a contact: an identifier, a name, a phone number
@dataclass(frozen=True)
class Contact:
    id: int
    name: str
    phone: str


class ContactsService:

    def __init__(self):
        self._contacts = [
            Contact(1, "Marie Durand", "01 23 45 67 89"),
            Contact(2, "Paul Martin", "06 12 34 56 78"),
            Contact(3, "Philippe Jandot", "02 98 76 54 32"),
        ]
        self._last_id = 3
        self._lock = Lock()

    def list(self) -> list[Contact]:
        with self._lock:
            return list(self._contacts)

    # the contact, or None if it does not exist
    def read(self, id: int) -> Contact | None:
        with self._lock:
            return next((c for c in self._contacts if c.id == id), None)

    def edit(self, id: int, name: str, phone: str) -> Contact | None:
        with self._lock:
            for i, contact in enumerate(self._contacts):
                if contact.id == id:
                    # a contact is immutable (frozen): replace builds a
                    # new one, which replaces the old one in the list
                    self._contacts[i] = replace(contact, name=name, phone=phone)
                    return self._contacts[i]
            return None

    def add(self, name: str, phone: str) -> Contact:
        with self._lock:
            self._last_id += 1
            contact = Contact(self._last_id, name, phone)
            self._contacts.append(contact)
            return contact

    def delete(self, id: int) -> Contact | None:
        with self._lock:
            contact = next((c for c in self._contacts if c.id == id), None)
            if contact is not None:
                self._contacts.remove(contact)
            return contact


def contacts_service() -> ContactsService:
    return current_app.extensions["contacts"]

    // confirmation of the forms that carry the data-confirmation="..." attribute
// Without JavaScript, these forms are simply sent without confirmation.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // the form to send if the user confirms

  // 1. we intercept the submission of the forms to confirm
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // the submission is suspended
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // the window appears
    });
  });

  // 2. the two buttons of the window
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // submission, WITHOUT firing the 'submit' event again
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • line 3: the code is enclosed in an anonymous function, which is executed immediately; its variables do not interfere with those of the other scripts on the page;
    • lines 4–6: the window, the message location, and the form awaiting confirmation;
    • lines 9–14: for each form that has a [data-confirmation] attribute, the [submit] event—triggered when the form is submitted—is intercepted. [preventDefault()] suspends submission; the form is put on hold, and its message ([dataset.confirmation], the value of the [data-confirmation] attribute) is displayed in the window, which appears;
    • lines 19–25: a single handler for clicks in the window: [event.target] is the element clicked; its attribute [data-action] specifies which button it is. “Yes” submits the pending form using the [submit()] method, which—unlike clicking a button—does not trigger the [submit] event (otherwise, the window would reappear); “No” hides the window.

    Without [JavaScript], the form is simply submitted without confirmation: the page remains usable. This is progressive enhancement: [JavaScript] adds convenience, but the application does not depend on it.
